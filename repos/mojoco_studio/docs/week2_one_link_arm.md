# Week 2: One-Link Arm and Rigid-Body Poses

This exercise connects the first half of Modern Robotics Chapter 3 to MuJoCo.
It creates the requested model with one link, one hinge, one actuator, and one
site at the end of the link. It then reads the body and site poses and checks
them using a rigid-body transformation.

## Run the experiment

From the repository root:

```bash
./build.sh one_link_arm
./build/one_link_arm
```

The program creates:

- `build/one_link_arm_poses.csv`: joint state, actuator force, and body/site
  poses at every control step.
- `build/one_link_arm_path.svg`: the site trajectory in the world $x$-$y$
  plane.

Open the interactive model with:

```bash
./simulate.sh one_link_arm
```

The Control panel's `shoulder_position` slider is a desired angle in radians.

## The MJCF objects

Read `assets/one_link_arm.xml` and identify these objects:

| MJCF element | Name | Role |
|---|---|---|
| `<body>` | `link` | Moving rigid frame and container for link elements |
| `<joint>` | `shoulder` | One rotational degree of freedom about local $z$ |
| `<geom>` | `link_geom` | Capsule shape with mass and collision properties |
| `<site>` | `tip` | Massless marker at $(0.6,0,0)$ in the link frame |
| `<position>` | `shoulder_position` | Servo whose control input is desired angle |

The world is also counted as a body by MuJoCo. The floor and pedestal are
world geoms, so `model->nbody` is 2 and `model->ngeom` is 3 even though the
robot itself has exactly one moving link. The pedestal has `contype="0"` and
`conaffinity="0"`, making it visual-only; otherwise its top touches the link at
the hinge and introduces unintended contact friction.

## Frames and transformation

Let $\{W\}$ be the world frame and $\{L\}$ the link body frame. At $q=0$,
the link points along $+x_W$. Its body origin is fixed at

$$
p_{WL} = [0,0,0.8]^T.
$$

The hinge rotates about $z$, so

$$
R_{WL}(q)=
\begin{bmatrix}
\cos q & -\sin q & 0\\
\sin q &  \cos q & 0\\
0      & 0       & 1
\end{bmatrix}.
$$

The tip site's coordinates in the link frame are

$$
p_L=[0.6,0,0]^T.
$$

Its world position is therefore

$$
p_W=p_{WL}+R_{WL}p_L
=
\begin{bmatrix}
0.6\cos q\\
0.6\sin q\\
0.8
\end{bmatrix}.
$$

Equivalently, using homogeneous coordinates:

$$
\begin{bmatrix}p_W\\1\end{bmatrix}
=
T_{WL}
\begin{bmatrix}p_L\\1\end{bmatrix},
\qquad
T_{WL}=
\begin{bmatrix}
R_{WL} & p_{WL}\\
0\;0\;0 & 1
\end{bmatrix}.
$$

The C++ program performs this calculation for every sample and compares it
with MuJoCo's `data->site_xpos`. Their difference should be near floating-point
roundoff.

## Reading poses from MuJoCo

First resolve names to integer object IDs:

```cpp
int body_id = mj_name2id(model, mjOBJ_BODY, "link");
int site_id = mj_name2id(model, mjOBJ_SITE, "tip");
```

Then access each object's slice in MuJoCo's flat arrays:

```cpp
const mjtNum* body_position = data->xpos + 3 * body_id;
const mjtNum* body_rotation = data->xmat + 9 * body_id;

const mjtNum* site_position = data->site_xpos + 3 * site_id;
const mjtNum* site_rotation = data->site_xmat + 9 * site_id;
```

`xpos` and `site_xpos` contain world-frame positions. `xmat` and `site_xmat`
contain row-major $3\times3$ world-frame rotation matrices. These are derived
quantities. Call `mj_forward` after manually changing `qpos`. This exercise also
calls it after the last `mj_step` in each control interval, because `mj_step`
integrates `qpos` at the end and derived Cartesian fields may otherwise describe
the preceding forward-dynamics evaluation rather than the newly integrated
configuration.

## Actuator semantics

Week 1 used a `motor` with `gear=1`, where `data->ctrl` represented torque.
This model uses a `position` actuator:

```xml
<position name="shoulder_position" joint="shoulder" kp="25" .../>
```

Here:

- `data->ctrl[actuator_id]` is a desired angle in radians.
- `data->actuator_force[actuator_id]` is the scalar force generated by the
  actuator; with unit gear on this hinge, its generalized contribution has the
  same numerical value as joint torque in N m.
- The command is updated at 50 Hz and MuJoCo physics runs at 500 Hz.

The program commands

$$
q_d(t)=1.0\sin(2\pi\,0.25t),
$$

which moves the tip along a circular arc. This is prescribed motion for model
inspection, not reinforcement learning.

## What to inspect

1. At $q=0$, verify that the site is near $(0.6,0,0.8)$.
2. At a positive $q$, verify that both site $x$ and $y$ match the analytic
   equations above.
3. Confirm that the third rotation-matrix column is $(0,0,1)$ because rotation
   is about $z$.
4. Compare `target_q_rad` and `q_rad` to see position-servo tracking lag.
5. Compare `actuator_force_nm` at slow and fast parts of the motion.

## Small experiments

Change one property at a time, rebuild, and compare the CSV:

1. Change the site local position from `(0.6, 0, 0)` to `(0.3, 0, 0)`.
2. Change the body position and predict the new world site coordinates first.
3. Change the hinge axis from `0 0 1` to `0 1 0` and derive the new rotation.
4. Add a site rotation such as `euler="0 0 0.4"`; position should be unchanged
   but site and body rotation matrices should differ.
5. Change actuator `kp` and observe tracking error and actuator force.

Experiments 1–4 directly exercise coordinate frames, rotations, homogeneous
transformations, and frame composition—the robotics topics studied this week.
