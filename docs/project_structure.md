# Project Structure and Storage

## Directory Ownership

| Directory | Purpose | Version controlled |
|---|---|---|
| `configs` | RM65 arm and camera configurations. | Yes |
| `docs` | Experiment design, training logs, evaluation, and maintenance notes. | Yes |
| `examples` | Reusable inspection, annotation, and hardware-test programs. | Yes |
| `artifacts` | Portable tokenizer artifacts needed across machines. | Selected artifacts only |
| `repos/lerobot` | Modified LeRobot implementation and RM65 adapters. | Yes |
| `scripts` | Stable recording, training, evaluation, dataset, and transfer entry points. | Yes |
| `runs/dataset` | Recorded and derived LeRobot datasets. | No |
| `runs/train` | Training checkpoints. | No |
| `runs/rollout_dataset` | Rollout recordings. | No |
| `runs/evaluation` | Offline evaluation results. | No |
| `runs/inspection` | Images generated by inspection and hardware-test scripts. | No |
| `logs` | Runtime and training logs. | No |
| `.cache` | Hugging Face and LeRobot caches. | No |

The large generated directories are symbolic links to external storage on the current workstation.
Source code must not rely on the physical mount path; it should use the project-relative links.

## Experiment Profiles

`scripts/train.sh` is the stable policy dispatcher. Reproducible dataset, policy, and optimizer
settings are kept separately in `configs/experiments/*.env`; common machine, cache, robot, rollout,
resume, and W&B settings remain in `scripts/env.sh`.

The default profile is `action_flow_v2_3_no_ki.env`. Select another profile without editing the
entry scripts:

```bash
EXPERIMENT_CONFIG=configs/experiments/action_flow_v2_4.env ./scripts/train.sh
```

Validate all profiles and their local dataset/tokenizer dependencies before starting a training
campaign:

```bash
./scripts/maintenance/validate_experiment_profiles.sh
```

The profile catalog is documented in `configs/experiments/README.md`. Existing ACT, Action Flow,
SmolVLA, and AFV2.4 configurations are retained, including historical profiles used to reproduce
earlier comparisons.

## Recording Profiles

Direct recording tasks are defined in `configs/recordings/*.env` and loaded by
`scripts/record_env.sh`. They are intentionally separate from training profiles: recording writes
only to source subsets, while training may read canonical merges or policy-specific derived data.

The default records one new `place_one_vegetable` episode. Select another task family with:

```bash
RECORD_CONFIG=configs/recordings/single_table_bus_table.env ./scripts/record.sh
```

Validate every recording target and robot configuration without connecting hardware:

```bash
./scripts/maintenance/validate_recording_profiles.sh
```

## Dataset Registry

`configs/datasets.yaml` is the authoritative lineage and retention registry for datasets under
`runs/dataset`. It records each dataset's role, parent datasets, construction tool, expected
metadata, policy usage, lifecycle, and retention state.

The current registry contains:

| Retention state | Count | Meaning |
|---|---:|---|
| `keep_active` | `2` | Current canonical robot data and Action Flow planning/box data. |
| `keep_source` | `12` | Direct recordings needed to rebuild or extend merged datasets. |
| `keep_historical` | `6` | Completed task datasets and the three YOLOE/SAM-derived AFV2 datasets. |

Validate paths, metadata, camera order, lineage references, and merge totals with:

```bash
python scripts/maintenance/validate_datasets.py
```

Validation is read-only. Superseded datasets remain registered as historical evidence of earlier
policy experiments and are not removal candidates.

## Evaluation Registry

`configs/evaluations.yaml` groups timestamped rollout directories by policy experiment rather than
requiring one handwritten entry per trial. It separates the official SmolVLA/AFV2.3/AFV2.4
comparison from historical ACT, Action Flow, and PI0 development runs, and it also registers offline
box-prediction and FAST diagnostics.

Validate that every rollout and offline-evaluation directory belongs to exactly one group with:

```bash
python scripts/maintenance/validate_evaluations.py
```

All current groups use `keep_official` or `keep_historical`. No rollout or evaluation artifact is
marked for deletion. Interactive evaluation sometimes saves camera videos without finalizing a
LeRobot episode, so zero episodes in `meta/info.json` does not imply that a directory is empty.

The standard `scripts/rollout.sh` reads the saved checkpoint configuration before constructing its
command. It therefore uses `num_steps` for SmolVLA/AFV2.3, `num_inference_steps` for PI-family and
AFV2.4 policies, and no unsupported step override for ACT. Robot arguments are selected from the
`mode` field in the RM65 YAML. Use `ROLLOUT_DRY_RUN=true` to inspect the resolved command without
loading the policy or connecting hardware.

## Checkpoint Retention

The policy in `scripts/maintenance/checkpoint_retention.json` uses two retention modes:

- `full_latest`: keep the complete final checkpoint, including optimizer state when it was available
  in the original checkpoint, so training can resume where possible.
- `model_only_latest`: keep only the final `pretrained_model` needed for inference and historical
  comparison.

Current comparison policies use `full_latest`. Historical experiments use `model_only_latest` by
default. Add an active experiment to the explicit policy before pruning if its optimizer state must
remain resumable.

Generate the current asset manifest with:

```bash
python scripts/maintenance/inventory_runs.py
```

Review checkpoint cleanup without changing files:

```bash
python scripts/maintenance/prune_checkpoints.py
```

Apply the reviewed plan with:

```bash
python scripts/maintenance/prune_checkpoints.py --execute
```

The generated JSON and Markdown manifests are stored under `runs/manifests`.

## Working Rules

1. Keep stable entry points at the top of `scripts`; place maintenance utilities in
   `scripts/maintenance`.
2. Save generated images under `runs/inspection` and logs under `logs`, not beside source files.
3. Keep one canonical robot dataset plus clearly named derived datasets. Do not delete source
   subsets until the canonical dataset and its metadata have been verified.
4. Record the exact dataset, policy configuration, and final checkpoint in the relevant training
   log before removing intermediate checkpoints.
5. Run the inventory after a major recording or training campaign so storage growth remains visible.
6. Add a new experiment profile instead of replacing values in `scripts/env.sh`; keep machine-only
   overrides outside version-controlled profiles.
7. Add direct demonstrations through a recording profile. Never point recording at an annotation
   or derived training dataset.
